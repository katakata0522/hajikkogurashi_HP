# 第2回 辛口コードレビュー：はじっこ勇者のインフレ魔塔

**レビュアー:** 私（リードエンジニア 兼 ゲームデザイン監査人）
**対象バージョン:** v1.1.0 (第1回修正後)

前回の修正で「スマホでの一筆書き無効バグ」や「セーブデータの簡易改ざん」は解決されましたが、ゲーム性（ホスピタリティ）および描画パフォーマンスをさらに追い込んだ結果、依然として実用上の以下のボトルネックが存在することが判明しました。

---

## 🚨 重大な指摘項目

### 1. 【ゲーム性】「絶対にクリアできない詰み盤面」がランダムに発生する
*   **問題点:**
    `generateFloorData` によるランダム生成では、セルの出現率だけで敵やアイテムを配置しています。そのため、高威力の敵が勇者の周囲を完全に囲んでしまったり、ポーションや武器をどう回収しても扉に到達する前にHPが確実に尽きてしまう「クリア不可能なデッドロック盤面」が確率で発生します。これではプレイヤーに理不尽な敗北ストレス（運ゲー感）を与えてしまいます。
*   **対策:**
    フロア生成後、勇者の初期HP/ATKと配置データを基に、**「HPを1以上残した状態で、鍵（またはボス撃破）を経由して扉に到達する有効な一筆書きルートが存在するか」**を深さ優先探索（DFS）で検証するバリデータ関数を実装します。クリア可能ルートが存在しない場合は、解が見つかるまで自動で再生成を繰り返す設計にします。

### 2. 【パフォーマンス】`document.elementFromPoint` による描画Reflow（カクつき）
*   **問題点:**
    前回の修正で導入した `document.elementFromPoint` は、タッチ座標からセルを特定するのに非常に確実ですが、PointerMoveの超高頻度（毎秒60回以上）でこれを呼び出すと、ブラウザはレイアウトツリーの再計算（Reflow）を強制されます。特にCPUスペックの低いAndroidのWebView環境では、なぞる線がカクつく原因になります。
*   **対策:**
    ドラッグ開始時（`pointerdown`）に、25個のセルの画面上の絶対境界座標（`top, left, width, height`）を一度だけ配列にキャッシュします。ドラッグ中（`pointermove`）は、ポインター座標がそのキャッシュされた矩形範囲内にあるかどうかを算術的（`x >= left && x <= right` 等）に判定します。DOMアクセスが完全ゼロになり、異次元の滑らかさになります。

### 3. 【堅牢性】状態（State）セッターにおける負の値のガード不足
*   **問題点:**
    `state.gold` や `state.hero.hp` に対する減算処理がゲームロジックの各所に散らばっています。万が一の計算誤差やバグにより、負の値（マイナス）が代入された場合、表示崩れやアンロックの不正挙動に繋がります。
*   **対策:**
    `state` をラップしている `Proxy` の `set` トラップにおいて、特定のプロパティ（`hp`, `gold`, `key`, `exp`）に負の値が代入されそうになった場合、自動的に `Math.max(0, value)` でガードする不変条件ガードロジックを追加します。

---

## 🛠️ 2回目の修正方針
1.  **DFS（深さ優先探索）解法存在バリデータの導入**: クリア不能盤面を100%排除。
2.  **セル境界ボックスキャッシュ方式への移行**: PointerMove時のリフローを完全排除（60FPS維持）。
3.  **Proxyセッターの型・負数ガードの強化**: 状態管理のセキュリティ・堅牢性を格段に向上。
